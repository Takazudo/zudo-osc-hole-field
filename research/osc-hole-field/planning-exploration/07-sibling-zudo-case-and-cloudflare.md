## Answer 1 - The exact recipe for zudo-osc-hole-field.zudolab.dev

### 1. Site URL in the doc framework config

File: `doc/zfb.config.ts` (generated by the template without `siteUrl`). Add inside `zudoDoc({ ... })`:

```ts
siteName: "zudo-osc-hole-field",          // or the chosen site title
githubUrl: "https://github.com/Takazudo/zudo-osc-hole-field",
// siteUrl host MUST equal the route pattern in doc/wrangler.jsonc
siteUrl: "https://zudo-osc-hole-field.zudolab.dev",
sitemap: true,
base: "/",                                 // already set by the template; do not change
```

What `siteUrl` drives in `@takazudo/zudo-doc@5.27.0` (verified by grep of the installed package): canonical link and `og:url`, `sitemap.xml` `<loc>` values, the `Sitemap:` line in `robots.txt` (only when `sitemap` is also true), and absolute URLs in `llms.txt`. When empty, all of these fall back to path-only or are omitted.

If a GitHub header link is wanted, also add `{ type: "component", component: "github-link" }` to `headerRightItems` (the lamp does this).

### 2. Wrangler config

File: `doc/wrangler.jsonc` (recommended dialect; avoids the TOML scoping trap).

```jsonc
{
  "name": "zudo-osc-hole-field",
  "compatibility_date": "<YYYY-MM-DD of authoring>",
  "workers_dev": false,
  "preview_urls": true,
  "routes": [
    { "pattern": "zudo-osc-hole-field.zudolab.dev", "custom_domain": true }
  ],
  "assets": {
    "directory": "./dist",
    "not_found_handling": "404-page"
  }
}
```

- No `main`, no `binding`, no `compatibility_flags`: the template has no adapter, so the site is fully static.
- `assets.directory` is relative to the config file, so `./dist` resolves to `doc/dist/`.
- No `account_id` in the file.
- Add `doc/.wrangler/` to `.gitignore` (the template's `_gitignore` does not list it).

### 3. Wrangler version

Two working precedents; pick one:

- zudo-circuit-doc style: no dependency, workflow runs `npx wrangler@<pinned> deploy --config doc/wrangler.jsonc` with the version in a workflow `env` (`4.85.0` there).
- zudo-case style: `wrangler` as an exact devDependency (`4.138.0` there) plus a `deploy:docs` script. Requires a lockfile change, and in a pnpm 11 workspace likely `allowBuilds: { workerd: true }` next to the existing `esbuild: true` (the lamp's `doc/pnpm-workspace.yaml` has both). UNVERIFIED whether pnpm 11 strictly needs it for a deploy-only use.

Current npm latest is `4.142.0`.

### 4. Deploy workflow

File: `.github/workflows/deploy.yml`, modeled on zudo-circuit-doc's `main-deploy.yml` with the project's own commands:

- `on: push: branches: [main]` plus `workflow_dispatch`
- `concurrency: { group: production-deploy, cancel-in-progress: false }`, `permissions: contents: read`
- checkout with `fetch-depth: 0` (the template sets `docHistory: true`, which reads git history)
- `pnpm/action-setup` (reads `packageManager: pnpm@11.5.2` from the root `package.json`), Node 24, Python 3.12 (the evidence validator is Python stdlib)
- `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm build`, `pnpm check:site`
- deploy step with `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in the step's own `env:`
- post-deploy smoke with retries: `/` expects 200, one known doc page expects 200, a missing path expects 404 (zudo-circuit-doc `scripts/smoke-url.sh`: 10 attempts, 15 s apart)

A separate credential-free `check.yml` on `pull_request` runs the same gates without the deploy.

### 5. Secrets (names only)

| Secret | Where | Status on `Takazudo/zudo-osc-hole-field` |
| --- | --- | --- |
| `CLOUDFLARE_API_TOKEN` | GitHub Actions repository secret | not set (`gh secret list` returned nothing) |
| `CLOUDFLARE_ACCOUNT_ID` | GitHub Actions repository secret | not set |

Token permissions needed for an assets-only Worker with `custom_domain: true`:

| Scope | Permission |
| --- | --- |
| Account - Workers Scripts | Edit |
| Account - Account Settings | Read |
| Zone - Workers Routes | Edit |

Zone Resources must include `zudolab.dev`. The knowledge base records that the minimal zone set varies by wrangler version; grant the full set, get a green deploy, trim later.

### 6. DNS and custom domain

There is no manual DNS step. `custom_domain: true` makes `wrangler deploy` create the DNS record and the edge certificate in the `zudolab.dev` zone on the first deploy. Preconditions:

- the `zudolab.dev` zone belongs to the account named by `CLOUDFLARE_ACCOUNT_ID` (true for zudo-case and zudo-circuit-doc, whose deploys succeed; whether the new repo will reuse the same account is the owner's choice)
- the token's Zone Resources include `zudolab.dev`

Expect one to several minutes before the hostname answers after the first deploy.

| --- | --- | --- |

## Answer 2 - Interpreting "static assets serving we'll do later"

Owner's words: "use doc domain as zudo-osc-hole-field.zudolab.dev , /cloudflare-wisdom static assets serving we'll do later".

### Recommended interpretation: the Cloudflare deployment itself is deferred

"Static assets serving" is the name of the hosting product. The knowledge-base article is titled "Workers Static Assets" (`workers/static-assets.mdx`), zudo-case's README calls its hosting "Cloudflare Workers Static Assets", and the lamp's workflow header says "deploys it to Cloudflare Workers static assets". The owner named the `/cloudflare-wisdom` skill in the same clause. Read this way, the sentence says: fix the domain now, do the Cloudflare hosting later.

Supporting facts: the target repo has no Cloudflare secrets, and the owner's four goals list the domain but no deploy.

| (1) Configure NOW | (2) Deferred static-assets-serving / deploy work |
| --- | --- |
| `siteUrl: "https://zudo-osc-hole-field.zudolab.dev"` in `doc/zfb.config.ts` | `doc/wrangler.jsonc` activation and first `wrangler deploy` |
| `githubUrl`, `sitemap: true`, keep `base: "/"` | `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` repo secrets |
| All internal asset URLs root-absolute (`/assets/...`), so the site works at the domain root | `.github/workflows/deploy.yml` |
| Credential-free `check.yml` on PRs (install, `pnpm check`, `pnpm build`, `pnpm check:site`) | Custom-domain attach, DNS and cert provisioning, propagation-tolerant smoke test |
| Every file under `doc/public/` listed in `circuit/publication/assets.json` with a reason, so `pnpm check:site` passes | PR preview deploys (`versions upload --preview-alias`) |
| A guard that no file under `doc/public/` or `doc/dist/` exceeds 25 MiB | `_headers` long-cache rule for hashed assets |
| A short doc page recording the domain and the deferred recipe (this section) | Any second Worker or R2 bucket for oversized assets |
| A follow-up issue titled for the deferred deploy | Rollback runbook (`wrangler rollback`) |

Optional in (1), and safe under either reading: commit `doc/wrangler.jsonc` now. It is inert without a deploy step, keeps the hostname in one reviewed place beside `siteUrl`, and can be validated with `wrangler deploy --dry-run`. A small test asserting `new URL(siteUrl).host === routes[0].pattern` prevents drift between the two files.

### Alternative reading: deploy the doc now, defer a separate asset host

Under this reading the doc Worker is deployed in this epic (as every sibling does), and "static assets serving" means a second host for heavy binary files, as zudo-case did with `zudo-case-preview.zudolab.dev`.

Evidence against needing that now: the handoff's 15 public files total about 5.4 MiB and the largest is `payload/doc/public/assets/osc-playground/workbench.html` at 2.86 MiB, far below 25 MiB. No second host is required for the handoff content as delivered.

When it would become necessary: if 3D models or fabrication archives above 25 MiB are published. zudo-case's two STEP assemblies are 26.4 MiB each and its two published oversized files are 31.5 and 32.9 MiB. A 318 x 298 mm board stack with 180 jacks and 144 controls can plausibly produce a STEP above 25 MiB.

### How to keep both readings cheap

Do everything in column (1), including the inert `doc/wrangler.jsonc`. If the owner meant the alternative reading, the remaining work is only secrets plus one workflow file.

## Answer 3 - Where zudo-case is a better model than zudo-led-lamp

### Better in zudo-case

1. **Static-only Worker.** No adapter, no `main`, no `nodejs_compat`, no `.assetsignore`. The lamp carries `@takazudo/zfb-adapter-cloudflare`, `main = "./dist/_worker.js"`, `compatibility_flags = ["nodejs_compat"]`, and a defensive `.assetsignore` rewrite in CI. The circuit template has no adapter, so the zudo-case shape is the one that matches.
2. **`workers_dev: false` with explicit `preview_urls: true`.** Production is served only on the custom domain. The lamp keeps `workers_dev = true` to make PR previews route.
3. **`*.zudolab.dev` hostname.** The lamp uses `takazudomodular.com`.
4. **JSONC config.** Not subject to the TOML scoping trap that the lamp's config needs a 5-line comment to warn about.
5. **Propagation-aware verification.** `curl --retry 60 --retry-delay 5 --retry-all-errors`, then full-GET SHA-256 comparison. The lamp's production workflow has no post-deploy check.
6. **Scaffold provenance record.** `.handoff/setup-record.json` captures CLI version, source commit, integrity hash, preserved paths, copied files, resolved versions and build verification. The new project should record the same for `create-zudo-circuit-doc@0.1.0` and for the R21 overlay.
7. **Handoff kept as immutable source, published copies kept separate.** `engineering/` and `project/` hold the raw handoff; only reviewed copies go to `public/`. `AGENTS.md` states source precedence and "keep old source folders immutable".
8. **Machine-checked ledgers.** `project/current-spec.json` plus `tests/ledger-plates.test.mjs`, `ledger-state.test.mjs`, `ledger-tables.test.mjs` fail on any dimension drift with a message naming model, plate and axis. This is the right pattern for "panel positions are fixed": a position ledger derived from the handoff grid, with a test that compares it against the KiCad PCB footprint coordinates.
9. **25 MiB guard and the chunked-streaming escape hatch.** Ready to copy if a large STEP must be published.
10. **Simple action pins.** Not better: zudo-case uses floating `@v4` tags; the lamp and zudo-circuit-doc pin actions by commit SHA. Follow the SHA-pinned style.

### Better in zudo-led-lamp (keep these)

- `doc/` layout, KiCad directories (`boards/`, `footprints/`, `symbols/`), component evidence skills: the same family the circuit template produces.
- Green-skip secret gating (`readiness` step). Correct while the deploy is intentionally deferred; zudo-case's hard failure would turn `main` red on every push until secrets exist.
- `paths:` filters on workflows so KiCad-only commits do not rebuild the site, with explicit entries for non-`doc/` inputs that change the site (`.claude/skills/**`, `footprints/**`, `boards/**/*.kicad_pcb`).
- Generated-output drift gate (`git add --intent-to-add` then `git diff --exit-code`).
- `doc/src/content/docs/how-to/ci-cloudflare-setup.mdx`: a runbook page for the token step.

### Closest overall model for hosting

zudo-circuit-doc's own doc site (`doc/wrangler.toml`, `.github/workflows/main-deploy.yml`, `scripts/smoke-url.sh`, `dev-docs/site-deploy.md`). ## Risks and blockers found while exploring

### create-zudo-circuit-doc refuses the target directory as it stands

`packages/create-zudo-circuit-doc/src/scaffold.ts` `checkDestinationCollision` uses `fs.readdirSync(destinationPath)` and throws when `entries.length > 0`. The target contains `.git/`, so it is not empty. There is no force flag. The handoff says the same ("The initializer is create-only. Never run it against a non-empty existing project").

Workable route: scaffold into a scratch directory with `--no-git`, then copy the result into the repo. The CLI does skip `git init` when the destination is inside a work tree, but it never reaches that point because the emptiness check runs first.

### The framework ships no deployment files

`templates/default` contains no `.github/`, no wrangler config, and no `siteUrl`. Grep for `wrangler|siteUrl|cloudflare|zudolab.dev|workers` in the template returned nothing, and the framework's published user docs contain no deploy guidance. Everything in Answer 1 must be authored by this project.

### Publication scan interacts with anything placed in doc/public

`pnpm check:site` runs `zudo-circuit-doc scan`, which fails on any file under `doc/public/` with a restricted extension (`.pdf .svg .json .step .stp .zip .csv .wrl .stl .glb .kicad_* .gbr ...`, 34 extensions) unless listed in `circuit/publication/assets.json` with a reason. The handoff supplies `publication-assets-to-add.json` with 15 entries for this purpose. Symlinks under the public root are always rejected. `_headers` has no restricted extension, so it would pass.

### Version skew between siblings

Copying lamp or zudo-case workflow files verbatim would pin pnpm 10.x and zfb 2.20.2. The template requires pnpm 11.5.2, Node >=22.18.0 and zfb 2.21.0. This machine has pnpm 10.30.3 on PATH with corepack 0.34.6 and Node v24.13.1; local commands must go through corepack.

### Template README is stale about npm publication

`templates/default/README.md` says the packages "are not yet published on npm". Both `create-zudo-circuit-doc@0.1.0` and `@takazudo/zudo-circuit-doc@0.1.0` are on npm as of 2026-09-27. The handoff reviewed commit `5d0e2b6`; the local clone is at `491f151`. Whether the published 0.1.0 tarball matches either commit is UNVERIFIED.

### Hard-fail secret gate would break main

If zudo-case's deploy workflow is copied while secrets are absent, every push to `main` fails. Use the green-skip or preflight pattern until the owner sets secrets, then switch to hard failure as `cicd/production-deploy.mdx` recommends.

### Public repo, public site

The repo is PUBLIC. zudo-case sets `noindex: true` and its README warns that noindex is not access control. Anything placed in `doc/public/` is world-readable once deployed.
